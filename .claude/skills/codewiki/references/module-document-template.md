# 模块文档模板

文档应帮助维护者理解职责、边界、关键实现和与其他模块的关系。只写与当前模块相关且可由源码或分析结果支持的内容。

## 通用规则

- 使用 MCP 返回的 `doc_path`，不要自行命名文件。
- 标题使用模块显示名称。
- 链接使用相对于当前文档的 Markdown 路径。
- 优先解释设计意图和关键流程，不逐行复述源码。
- 提及具体组件、API 或行为时，给出代码路径或组件 ID。
- 没有证据的章节可以省略，不要为满足模板填充推测内容。

## 叶子模块

推荐结构：

```markdown
# 模块名称

## 用途

说明模块解决的问题、职责和边界。

## 架构

展示核心组件及其关系。仅在关系明确时添加 Mermaid 图。

## 核心组件

说明关键类、接口、函数或入口的职责、公开行为和重要实现约束。

## 主要流程

描述模块编排的重要流程。适合时使用流程图或序列图。

## 依赖关系

区分内部依赖、其他 CodeWiki 模块和外部系统。链接已生成的模块文档。

## 设计注意事项

记录错误处理、状态管理、扩展点、性能或安全方面的重要实现。
```

叶子模块不要再次拆分子模块。若上下文表明模块划分明显不合理，停止该模块生成并要求 MCP 重新分析。

## 父模块

推荐结构：

```markdown
# 模块名称

## 用途

说明该逻辑分组的整体职责和系统边界。

## 架构

以直接子模块为节点，展示子模块间关系。

## 子模块

逐个概括直接子模块并链接其文档。

## 跨模块流程

描述跨越多个直接子模块的关键流程。

## 横切关注点

总结多个子模块共同遵循的约定、数据模型、错误处理或扩展机制。
```

父模块必须保持概述级别：

- 不复制子模块的组件列表和详细实现。
- 不加载或总结非直接后代，除非解释端到端流程确实需要。
- 不把单个类画成父模块架构图的主要节点。

## 内容质量

优先回答：

- 为什么存在这个模块？
- 它负责什么，不负责什么？
- 哪些组件或子模块承担核心职责？
- 数据或控制如何流经模块？
- 它依赖谁，谁依赖它？
- 修改该模块时最容易破坏什么？
